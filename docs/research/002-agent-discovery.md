## 3. 模型接入前置核实

截至本次调研，OpenCode 官方模型页列出 DeepSeek V4.1 Flash Free，并明确为限时免费。免费模型与同名付费模型应区分，不能仅凭展示名推断模型 ID、调用地址或计费方式。

官方仓库有外部客户端触发 `FreeTierError` / HTTP 403 的直接报告；官方 Console 也提供其他工具调用 API 的说明，不能把一般 API 可用性直接套到免费层。

本轮补充核实发现：[官方 Inference API 的 Authentication 节](https://opencode.ai/v2/docs/console/api/inference/)明确说明免费聊天模型可不带认证头调用。此前只依据模型页、故障报告和匿名请求，没有先核对该认证段落，核实不完整。不能把服务返回的一次错误描述成官方已经明确禁止所有外部调用。

本轮最小直连实测：向官方当前列出的 `https://opencode.ai/inference/openai/v1/chat/completions` 发送 `deepseek-v4.1-flash-free` 的单条文本请求；使用公开匿名凭据 `Bearer public`，如实标识客户端为 `dbts-search-probe/0.1`，未读取用户密钥、未伪装 OpenCode 客户端。响应为 HTTP 403：

```json
{"type":"error","error":{"type":"FreeTierError","message":"OpenCode's free tier can only be used from within OpenCode. Download it at https://opencode.ai and keep building."}}
```

结论限定为：上述匿名直连方式未通过，不能作为当前 Python 服务的已验证模型接入。用户账号密钥、其他官方支持接入方式、工具调用及结构化输出尚未实测；也没有确认用户账号的额度和权限。不能把这个结果扩大成所有接入方式都不可能，或直接认定必须付费。

随后按上述官方说明，去掉 Authorization 头，对 `deepseek-v4.1-flash-free` 重新发送最小文本请求，仍返回同一 HTTP 403 / `FreeTierError`。因此当前证据是“文档允许免认证，当前独立客户端请求未通过”，服务端策略、版本或账号条件仍有未解释差异。

### 3.2 官方 OpenCode 运行时路径

官方还提供 [headless HTTP server](https://opencode.ai/docs/server/) 和 [SDK](https://opencode.ai/docs/sdk/)，可以通过真实 OpenCode 运行时创建会话与发送消息。这与 Python 直接调用模型 API 是不同集成方式；不能因前者存在就声称后者已经通过。

本机安装的 CLI 为 `1.19.0`。在工程外空目录中，通过 `opencode run --pure --model opencode/big-pickle` 做最小测试：禁止全部工具的配置返回同一 403；去掉该权限覆盖、采用正常配置后，成功返回 `OK`，退出码 0，官方运行事件记录 `cost: 0`。测试指定免费模型、禁用分享、使用独立临时目录，没有工具执行事件或项目修改。

随后相同正常配置下，指定 `opencode/deepseek-v4.1-flash-free` 也成功返回 `OK`，退出码 0，运行事件记录 `cost: 0`。这证明用户原选 DeepSeek 和 Big Pickle 均可通过当前官方 CLI 运行时调用，不应因独立 HTTP 返回 403 就换供应商。

权限配置与请求内容会影响当前免费层校验，但没有完成控制变量审计，不能由这组结果断言所有限制都只由权限配置造成。这是当前环境下的文本调用验证，不是独立 Chat API、业务工具或产品流量使用条件的完整验收。

运行时文本验证已通过，接下来仍需验证业务工具调用、受限执行与结果回传，再决定它只是本地试验后端还是成为服务依赖。后者会增加一套已有 Agent 循环与进程管理，需要与已确认的 LangChain harness 边界重新取舍；不能用虚构客户端标识把直连失败包装成官方支持的 API 方案，也不能把原生编码工具直接暴露给产品用户。

## 4. 已确定的服务边界与待确认交互协议

建议的完整调用关系：

```text
uni-app 首页入口 / Agent 会话
    → Java 统一入口
    → Python agent 服务
    → LangChain harness（会话状态、模型、受限工具、恢复）
        ├─ 内容检索 / 内容读取
        ├─ 已完成 Java 业务的受控接口（逐项开放）
        └─ 客户端本地能力的类型化动作 / 真实执行回执
```

Python 服务可采用 FastAPI；继续保留轻量 LangChain 方案。新增多轮上下文与工具执行状态，但不因产品定位扩大就默认加入子 Agent、长期记忆、向量库或消息队列。需要这些组件时由真实任务和验收证明。

Java 负责对外入口及已有业务接口，Python 负责模型和工具编排。Java 转发模型错误、超时和取消，不自动重放整轮 Agent 请求；模型恢复策略集中在 Python 一层，避免 Java、SDK 和 LangChain 各自重试导致次数相乘。

客户端本地状态（制作进度、部分搭配等）继续由现有工具函数负责。模型生成的是受限动作请求，前端或 Java 的实际执行结果才是成功依据；前端需要回传成功、失败或取消，再进入下一次模型判断。动作不因“明确指令直接执行”就绕过原功能的参数、状态与权限约束。暂停/回执接口按具体能力落实，不声称现有页面已具备该桥接协议。

工具仅开放已经完成且允许当前用户使用的能力；不开放 shell、任意文件写入或任意 SQL。联网能力只搜索、读取公开网页，不能把“读取网页”扩展为执行网页内命令。个人信息仅在具体功能需要且身份边界成立时提供，不把所有本地用户数据塞入模型。现有模拟登录不能充当真实用户鉴权。模型密钥仅在服务端配置。

### 4.1 意图与动作执行规则（已确认）

- 明确对象下说“下一步”“保存这个搭配”“重新制作素蒸茄子”时，执行该已开放动作；不因为动作属于重置或保存就再插入一轮固定确认。
- “要不换一个”“处理一下”“这个不要了”等无法确定具体动作或对象的表述，先围绕缺少的内容追问。后续仍含糊则继续澄清，不以超时、追问次数或模型置信度替代用户选择。
- 建议或条件讨论，例如“重新制作会怎么样”，只说明影响，不当成执行指令。
- 澄清期间不执行待确认的改变状态操作。明确后复用已知上下文，不让用户重复提供已确定的信息。
- 同一个用户意图可能涉及多个动作；每一步均以实际执行结果推进，失败不宣称整件事已完成。

### 4.2 独立助手页与多入口（已确认方向）

- 第一版接通首页入口并落地独立会话页；后续其他页面复用同一个入口函数和同一个助手页，不复制会话逻辑。
- 入口可以提供当前页面、内容 ID 以及用户刚输入的话。入口上下文是理解任务的线索，不是自动执行命令；进入某道菜页面的助手不等于用户要求重置或开始制作。
- 进入时有明确已选会话则继续该会话；未指定则恢复本机最近会话，首次使用创建会话。入口来源本身不触发新建会话或清空旧对话。此为统一会话的实现建议，后续显式“新对话”入口可创建独立会话。
- 当前入口内容与会话中的未结束任务冲突时，不默默覆盖动作对象；结合当前用户表达，仍不清楚则追问。例如先前制作素蒸茄子，后来从名画页进入并说“继续”，应确认继续哪项任务。
- 初始界面只显示当前任务所需的输入、简短回答和相关卡片/操作；用户跨任务提问时再展示其他已开放能力。能力发现不等于隐藏操作结果或主动执行未请求的动作。
- 从助手打开原业务页后仍能返回原会话；重新进入时读取实际最新状态，不以聊天记录中的旧进度覆盖业务数据。

### 4.3 历史与运行状态的区分

本机保存用户/助手可见消息、引用内容及必要的会话标识，满足离开和重开后续聊。模型上下文只传当前任务需要的有限历史，不把全部历史永久拼进每个请求；具体截取量在模型接入后验证。

聊天记录只能证明曾经说过什么，不能证明制作进度、收藏等目前仍是什么状态；当前业务状态仍由原执行端读取。恢复历史时，已经完成的动作不自动重放；上次中断且执行结果不明的动作先查证，不能仅凭存储中的请求再次执行。

首版不承诺服务进程崩溃后的逐 token 恢复，也不把本地保存扩展为跨设备同步。新会话、清除聊天记录和重置制作进度属于不同操作，不互相隐式影响。

## 5. 数据格式建议：目录、模型选择、前端响应分别约定

以下字段与接口均为提案，待下一轮确认后冻结。

### 5.1 内容目录

小规模内容优先使用 UTF-8 JSON，供前端与 Python 共享读取或在构建时生成；运行时使用普通内存检索。已结构化的 JS 内容表通过受控导出生成目录，不再手工复制全文。Vue 中分散的条目只整理本次实际收录的部分，不顺手重构全站。

单条目录示例：

```json
{
  "id": "food:suzhengqiezi",
  "domain": "food",
  "kind": "detail",
  "title": "素蒸茄子",
  "summary": "茄条蒸软后拌入蒜香调味汁，入口柔软，做法清简。",
  "image": "/static/food-details/suzhengqiezi.jpg",
  "route": "/pages/food/detail/content?key=suzhengqiezi",
  "aliases": ["蒜香蒸茄子"],
  "tags": ["素食", "茄子", "蒸菜"],
  "searchText": "由已有简介、材料与步骤导出的可检索文本"
}
```

- `id` 跨模块唯一，不复用分类内局部数字 id；四个 domain 暂建议 `clothes | food | lodging | travel`。
- `kind` 表达实际可用的内容入口种类；未完成条目不以分类入口替代收录。
- `title / summary / image / route` 来自已核对的项目内容，不能由模型改写。`/static/` 是应用内资源路径，不由 Python 拼成服务器图片 URL。
- 别名和标签是检索辅助元数据，不能把未经支持的年代、身份、饮食限制或历史用途写进去。
- 来源和历史归属限定沿用原有资料，必要时提供给检索判断；不把现代做法示例当宋代原方。
- 目录检查既验证页面存在，也核对路由参数与目标条目对应，避免“打开了页面却展示另一项”。

### 5.2 Agent 消息与动作

“只输出 selectedIds”只适合原搜索场景，不能作为整个项目助手的唯一输出。建议一轮结果区分说明文本、内容引用和动作请求，例如：

```json
{
  "text": "找到素蒸茄子，可以查看材料和制作步骤。",
  "selectedIds": ["food:suzhengqiezi"],
  "actions": []
}
```

说明文本允许围绕已有内容生成简短解释，不扩写无依据的事实。卡片字段仍按合法 ID 回填。动作使用逐项定义的名字和参数，不能让模型直接返回任意 JS、路由或已成功结论；按照第 4.1 节判断直接执行还是追问，不额外套用上一轮的重置/删除确认规则。

服务端检查 schema、引用 ID 与能力权限；具体工具的参数由其 schema 定义。结构化方式按接入实测选择，不假定 OpenAI 兼容网关必然支持原生 JSON Schema 和同时使用工具。

### 5.3 HTTP 响应

新增多轮会话，不再使用孤立的 `query` 作为完整请求。请求至少需要当前消息、会话标识和本轮标识；重试与动作回执要能对应原回合。客户端状态按功能提供最少必要快照，不上传整份本地存储。

建议的接口形状如下；字段先明确含义，端点和 JSON / 流式传输在实现方案中统一：

```json
{
  "sessionId": "example-session",
  "turnId": "example-turn",
  "message": "继续刚才那道菜",
  "context": {
    "entry": "food_detail",
    "contentId": "food:suzhengqiezi"
  }
}
```

普通 JSON 模式沿用 Java 的 `ApiResponse` 外层；以下为完成一轮后的 data 示例。若最终采用流式，回合状态和最终结果语义仍保持一致：

```json
{
  "sessionId": "example-session",
  "turnId": "example-turn",
  "status": "completed",
  "text": "找到素蒸茄子，可以查看材料和制作步骤。",
  "items": [
    {
      "id": "food:suzhengqiezi",
      "domain": "food",
      "kind": "detail",
      "title": "素蒸茄子",
      "summary": "茄条蒸软后拌入蒜香调味汁，入口柔软，做法清简。",
      "image": "/static/food-details/suzhengqiezi.jpg",
      "route": "/pages/food/detail/content?key=suzhengqiezi"
    }
  ],
  "actions": []
}
```

回合状态至少区分运行中、等待动作回执、已完成、失败和用户停止，最终字段随协议冻结。检索没有内容是正常业务结果，区别于回合失败。恢复策略见第 6.1 节；不再把“自动切关键词搜索”设为默认恢复。

客户端动作与回执至少关联同一个 `sessionId / turnId / actionId`。动作携带已开放的 `name` 和该能力定义的 `args`；回执给出 `succeeded / failed / cancelled` 以及需要回填的实际结果。`actionId` 由应用管理，不能由模型重试时随意换号；这些标识不能代替业务鉴权或真实执行状态。具体字段以能力契约为准，不先做通用插件执行平台。

## 6. 工具调用建议

按能力清单开放工具，不把“只有一个检索工具”固化为产品能力上限。优先复用现有内容和业务实现，例如：

```text
search_content(query, domains?, limit?) → candidates
get_content(content_id) → verified_content
web_search(query, max_results?) → sources
read_webpage(url) → cited_content
已完成 Java 业务的具体工具 → 实际业务结果
已完成客户端功能的具体动作 → 客户端执行回执
```

`domains` 仅允许目录中的模块；候选记录提供 ID、标题、原有摘要和必要的检索证据。模型看到的业务数据不必包含可执行路由；最后由服务端回填。候选上限由服务端约束。

例如“女子出门穿什么，中午吃什么”：模型可分别检索服饰和饮食，再合并选择真实 ID。工具执行普通内容查询，不允许模型提交 SQL、代码、任意路径或 URL。

优先采用名称、别名、标签和正文检索；先用验收样例测白话召回，再判断是否需要中文分词或向量检索。不得把大模型可以理解白话等同于底层检索已具有语义召回能力。

原草案“3 次模型调用、15 秒”是单次搜索的参数提议，不直接沿用于交互 Agent。需要分别设定单次模型传输重试预算、单轮推理/工具预算及总截止时间，显式区分逻辑调用、传输重试和参数修正。等待用户操作时不占用模型网络超时；具体数值在真实模型接入和任务清单确认后确定。

### 6.1 Codex 参考与本项目恢复提案

源码依据为 OpenAI 官方仓库固定提交 `111362a6a0a92d08885b1ae62d3760714907ad94`，不声称与当前桌面客户端的所有内部行为完全一致。本机 npm CLI 只有启动器和二进制，不以安装版本推断源码细节。

Codex 的已核实做法：

- [HTTP 临时故障有独立分类和重试](https://github.com/openai/codex/blob/111362a6a0a92d08885b1ae62d3760714907ad94/codex-rs/codex-client/src/retry.rs#L22-L115)；[流恢复另有预算及恢复提示](https://github.com/openai/codex/blob/111362a6a0a92d08885b1ae62d3760714907ad94/codex-rs/core/src/responses_retry.rs#L87-L175)。换传输协议不等于换模型或关键词搜索。
- [优先使用 Retry-After](https://github.com/openai/codex/blob/111362a6a0a92d08885b1ae62d3760714907ad94/codex-rs/http-client/src/retry_after.rs#L13-L48)，本地等待采用退避；不机械复制其面向编码任务的等待时长。
- [同一活动回合恢复时从已记录历史重建请求](https://github.com/openai/codex/blob/111362a6a0a92d08885b1ae62d3760714907ad94/codex-rs/core/src/session/turn.rs#L1740-L1756)，[最终错误后允许继续会话](https://github.com/openai/codex/blob/111362a6a0a92d08885b1ae62d3760714907ad94/codex-rs/core/src/session/turn.rs#L886-L901)。这不代表逐 token 断点续传或进程崩溃后的完整恢复保证。
- [工具参数和普通工具错误反馈给模型](https://github.com/openai/codex/blob/111362a6a0a92d08885b1ae62d3760714907ad94/codex-rs/core/src/tools/parallel.rs#L97-L121)，不能据此推断所有写操作都能自动防重。

据此提出适合本项目的策略，尚未实现：

| 情况 | 建议行为 |
| --- | --- |
| 临时网络失败、模型超时、明确可恢复的限速或服务端错误 | Python 层有限重试，退避与抖动；服务方有 Retry-After 时遵守，超过整轮剩余预算则结束而非无限等待 |
| 无权限、密钥错误、额度耗尽、无效配置 | 明确失败，不盲重试；此前免费模型 403 不属于增加重试就能解决的问题 |
| 工具参数或最终结构不合法 | 以简短受控错误反馈给模型，允许有限纠正；不重跑此前成功的动作 |
| 业务拒绝、条目不存在、条件不满足 | 工具返回真实业务结果，由 Agent 追问或调整方案，不当成网络重试 |
| 传输中断前已有工具完成 | 保存工具调用和实际结果，从这些状态继续；未拿到最终状态的动作先核实，不擅自宣称成功或再次执行 |
| 重试预算耗尽 | 保留当前会话与已完成结果，显示简短失败及重试入口；普通检索可另设独立入口，不能代替原任务的完成结果 |
| 用户停止 | 取消模型请求及退避等待；已经提交并执行的业务动作不会因取消自动撤销 |
| 格式正确但事实没有依据 | 不通过多重传输重试处理；依靠内容来源、引用检查和验收查询约束 |

对真正改变状态的能力，必须按动作性质设计重复执行规则：读取可以重试；“设置到某步骤”等应保持同一操作重复后的结果一致；“下一步/新增/发布”等不能因整轮重放重复发生。动作结果未知时不能换一个操作 ID 再试，先确认原动作。避免笼统声称 exactly-once。

优先复用 LangChain 的 [ModelRetry / ToolError / ToolRetry 中间件](https://docs.langchain.com/oss/python/langchain/middleware/built-in)，显式配置可重试异常与最终失败行为，不照抄默认“所有异常”或把错误包装成成功回复。若由 LangChain 管重试，应关闭或统一供应商 SDK 的重复重试；Java 不再叠加自动重放。是否支持 Retry-After 必须在所选适配器上验证。

断流后可以保留已完成内容，但不能把半截参数作为工具调用执行；用户可见文本若需要重新生成，应更新同一回合，避免把重复输出拼接在一起。具体流式协议取决于双端展示选择。

### 6.2 联网查证（用户已确认）

项目内导航、内容与功能状态首先使用项目自己的数据。资料未覆盖的问题可搜索和读取公开网页，再给出带来源的回答；网页结果不自动变成项目卡片，不生成本地虚构入口。查询没有找到可靠依据时说明无法确认。

检索结果至少保留标题、原始 URL、正文证据及抓取时间；回答中的来源链接必须对应实际返回的结果，不能让模型编造链接。宋史与文物问题优先博物馆、大学、原始文献等资料，对作者、年代及传称保留必要限定。

网页内容作为资料处理，不作为修改系统指令或执行项目动作的授权。外部搜索只发送当前问题所需的公开关键词，不发送完整聊天记录或私有业务数据；网页读取限制在公开 HTTP(S) 页面。

免费网页工具候选为 Tavily Search / Extract：[官方额度文档](https://docs.tavily.com/documentation/api-credits)列每月 1,000 免费 credits，无需信用卡；basic search 每次 1 credit、advanced search 每次 2 credits，Extract 单独计量。因此不能把额度称为“固定 1,000 次完整联网回答”。尚未注册账号或获得 Key，不声称已实测可用。供应商仍为提案，不自动开通付费。

当前聊天中可用的网页工具和连接器是研发工具，不等于最终产品已拥有相同权限或额度。项目需要自己的运行时接入配置；搜索服务额度耗尽时返回明确的联网失败，不谎称已查证。

## 8. 建议实施顺序与验收

| 阶段 | 交付 | 通过条件 |
| --- | --- | --- |
| A 接入验证与能力核验 | 真实模型最小调用、全站能力清单、内容目录、十二套流程回归 | 真实接入通过；每项收录真实完成，未完成动作排除；十二套有真实问题则先修 |
| B 会话与工具契约 | 多轮会话、内容工具、能力工具、卡片回填及有限恢复 | 追问沿用正确上下文；不执行目录外动作；空结果与失败分开；重试不重复已成功动作 |
| C 客户端与 Java/Python 联调 | 首页进入会话、前端动作与实际回执、结果和状态展示 | 双端能查询并使用已开放能力；制作进度与原页面一致；真实执行失败不显示成功 |
| D 回归与交付 | 自动化约束、真实模型样例、浏览器及开发者工具记录 | 根目录 `npm run verify` 全部通过，并完成下表人工/真实模型检查 |

验收样例候选：

- “做素蒸茄子”→“下一步”→离开→“继续刚才那道菜”：使用十二套已核验流程中的真实内容与进度；Agent 与原制作页保持一致，回执未成功不推进。
- “重做这道菜”：对象和意图明确后直接执行，只重置当前菜；重复网络请求不反复改变状态。
- 当前菜已明确时说“重新制作这道菜”：直接执行一次，不额外弹出固定确认；问“重新制作会怎么样”只解释，不执行。
- 对象不明时说“换一个”或“继续”：追问；用户仍未说明则继续澄清，不能擅自重置、换菜或推进步骤。
- 离开助手、重开应用后恢复原对话；读取最新真实制作进度，已完成动作不因会话恢复而再次执行。
- 从首页与未来业务入口进入的是同一个助手页；入口变化不清空旧会话或自动执行动作，原页面返回后仍能接续。
- “宋代女子出门穿什么，中午吃什么”：返回服饰和饮食的真实内容；不能把官服当女子日常服饰。
- “想体验一天宋代文人的生活”：按收录内容返回相关模块；不为凑齐衣食住行编造条目或宋代归属。
- “不想吃肉，想做一道蒸菜”：命中有内容依据的菜品，验证白话与约束召回。
- 搜不存在的条目：显示没有收录内容，不用其他卡片冒充。
- 模型返回虚构 ID、重复 ID、工具预算耗尽或供应商超时：不渲染虚假卡片，不无限重试。
- 详情 id 不对应、无参数却恒显示默认详情的页面：目录验证应失败。
- 对首批以外的每一项已完成能力，增加对应的成功、失败与重复请求验收记录，才能加入工具列表；不只验收搜索后宣称覆盖整个项目。
- 网络短暂失败后继续当前会话，不清空此前卡片与成功动作；403/额度耗尽不反复请求；用户停止后不继续后台自动重试。
- 项目没有覆盖的文化问题：实际搜索并读取证据，给出对应来源；搜索失败或没有可靠依据时不声称已查证，也不返回虚构项目卡片。
